# 文档结构规范（八节骨架）

每章的"写什么、怎么写"。体裁参照《TriDao FA-NPU A5 v3 反向确定性方案详设》
（v2-stream 累加方案文档）：先问题后方案、先小案例后一般规则、
机制叙述配逐步推演、资源与流水单独成章。

## 0. 标题

`《算子/方案名 + 版本分支》`，如 `TriDao FA-NPU A5 v3 反向确定性方案详设（det-cmp-v2-stream）`。
标题下一行可放元信息：作者、日期、状态（草案/评审/定稿）、对应代码分支与 commit。

## 1. 需求分析

两段话讲清**问题与必要性**，不要方案细节：

- **需求背景**：业务/功能诉求是什么（如：反向结果需要逐位可复现）。
- **功能分析**：问题的技术根因。写法 = 先给定理/事实，再给后果。
  例：「浮点加法不满足结合律 → 若按随机顺序对反向分块梯度累加，两次反向得到的
  梯度不一致。FAG 反向存在 dq/dk/dv 分块梯度累加，非确定性方案按各 cube 核的
  完成时间顺序累加，无法保证两次运行累加顺序一致。」

## 2. 原型设计

- **接口函数**：签名（语言级），关键参数逐个说明取值与含义；
- **开关参数**：如 `deterministic`：True = 确定性方案 / False = 非确定性方案；
- **相关输入输出说明**：张量 layout、dtype、约束（对齐、最大长度、head 关系）。

## 3. 特性实现方案

全文档的主体。结构：

1. **总述**：方案一句话（如"调度先行：让累加按构造好的次序发生，而不是收集后归约"）；
   对照非确定性方案的做法（如"完成即 AtomicAdd"）。
2. **计算逻辑**：按硬件侧分述（Cube 计算逻辑 / VEC 计算逻辑）——
   谁写 workspace、谁做归约/落盘、顺序由什么保证。
3. **小而典型的案例**：给定最小输入（b=1、n2=1、g=1、S1/S2 各 2~3 块），
   **逐轮写出**每块的去向：任务分配 → 每轮的 accumList → 每次合并的算式
   （如 `v0: dk(s2o=0, rblk=0) = dk(s1o=0, s2o=0, c0, rblk=0) + dk(s1o=1, s2o=0, c3, rblk=0)`）。
   案例必须具体到读者能照着重演。
4. **分支/规则表**：把"什么条件走什么动作"列成表（简单表用 Markdown；
   有合并/配色用 table_image 出图）。

## 4. Tiling 切分

- 数据布局（如 `[T, N, D]` 交错、GM 行步长 = headNum × headDim、跨步访存）；
- 轴序（如确定性分支用 `b→n2→g→s1→s2`，与非确定性 `b→n2→s2→g→s1` 的差异与原因）；
- tile 大小选择（BLOCK_S1/BLOCK_S2）与对齐。

## 5. 分核策略

任务如何铺到核上：分核轴、每核的任务序列、轮次结构、空转/裁剪规则。
有调度算法时给出 (round, core) → 任务的纯算术描述或调度矩阵图。

## 6. 片上内存资源设计

- workspace 布局（各区大小、对齐、谁清谁写）；
- L1 / UB / L0C 槽位预算表（每槽内容、大小、复用关系）；
- 能省则省的论证（如"dqWorkSpace 只需 BLOCK_S1 × Dqk 的原因：外循环 Q，
  每轮未算完分块至多 1 个"）。

## 7. 流水设计

- **非确定性方案的流水**（基线，简述）；
- **确定性方案的流水**：新增的阶段（如每轮末尾的 ProcessVecDTM）、
  与前/后轮的衔接（如 VecDTM 与下一轮 Preload C12 重叠）；
- **旗标/同步表**：每个 flag 的 置 1 条件 / 含义 / 谁等谁
  （这类表常有合并单元格 → table_image 出图）；
- 有甘特图时放甘特图（可用 seeten-draw 画 PPT 页后导出 PNG）。

## 8. 测试设计

- **正确性**：golden 一致、确定性验证（同输入多次运行逐位一致）、边界/异常用例；
- **性能测试**：环境（芯片/CANN/驱动/频率）、**计时口径**（必须写：
  msprof Task Duration 还是 event 端到端、warmup/repeat、median or min）、
  用例矩阵（shape 表：b n g s2 s1 d causal/dense）、结果表（核时、对比、加速比）、
  结论与后续项。口径细则见 `references/perf-method.md`。

## 文风约定

- 句子短；术语首次出现给英文原名与缩写（如 `Data Terminator Module（DTM）`）；
- 索引记号统一：`s1o`/`s2o`（块索引）、`c0..ck`（核）、`rblk`（块内行组）、`T0/T1`（轮）；
- 每个断言尽量可回读：数字给来源，规则给代码位置（文件:行）；
- 对比用"非确定性 vs 确定性"并列写，差异点加粗；
- 图片只放必须合并/配色的表格与结构示意图；流程尽量文字化（可检索、可 diff）。


## 写作风格与数据表约定（实践沉淀）

### 叙述体，不是演示体

正文用**长段落**写：先背景后结论，用"因为 / 所以 / 之所以"把因果关系串起来，
一段话把一件事讲完整。**不要**把 PPT 式短句碎块直接搬进文档（"· xxx。· yyy。"）——
那是演示体，读者拿不到上下文。伪代码、表格、图注之外的正文一律段落化。

### 自包含

- 不写"详见 xxx.pptx / 参见某个演示文件"——需要的内容以图片或文字**纳入本文**；
- 已有演示文件的页面是首选配图：拷到工作目录、按需修改（去页号/加粗）、真渲染
  （见 `pptx-render.md`）；页面里的伪代码与数据面板已经是正文内容，**不要再抄一遍**；
- 代码位置等"溯源信息"统一放附录表格，正文不夹杂文件名。

### 版本纪律

一份详设描述**一个版本**。后续改进（性能优化、调度修正）另写独立文档；
本文不出现改进版本的代号、机制与对比数据——否则读者无法判断正文描述的是哪一版。

### 数据表

- 用例清单**拆列**：`# / case / b / n2 / g / s2 / s1 / d / mask`（便于检索排序）；
- 重复段长**简写**：等长段写 `8×512`，不等长保持 `256+384`（避免一行几十个 `+`）；
- 性能明细给全：核时、比值（达标加粗）、GM 行、pass 行；
- 表格配色**克制**：白/灰斑马行即可，彩色最多一组且要有明确语义（如"唯一强调列"），
  能不用就不用。

### 事实核实

写机制描述前**回读实现代码**确认行为（关键路径、同步、落盘时机等），
代码行为与直觉描述不一致时以代码为准；曾因"想当然"把 per-task 落盘写成
per-column 累加，后经代码核对修正。


## 性能优化文档（另一体裁，模板见 templates/op-perf-opt-template.md）

一篇详设描述**一个版本**；性能优化是**另一篇文档**，描述版本演进（v0 → v1 → v2 …）。
骨架：

```
1. 背景与目标      —— 基线差距用数字量化（几何均值 + 对参考比值），目标写成清单
2. 优化方法论      —— 测量纪律单独成章（这是结论可信度的前提）
3. 优化项一        —— 问题 / 方案（配图）/ 正确性 / 收益（四段式）
4. 优化项二        —— 同上，跨版本逐章累加
5. 探索与排除      —— 负结果台账（尝试 / 做法 / 实测结果 / 处置）：关闭、回退、
                     暂不做、后续项都要写——它避免后来者重复投入
6. 性能评测        —— 口径 / 版本递进（表+柱状图）/ 全对比矩阵 / 分 pipe 归因
7. 结论与后续      —— 现状 + 下一步重心（量化到机制）+ 记录的后续优化点
附录               —— 版本与提交对照
```

### 收益与差值的写法（防歧义）

- 速度类比值**方向写死在列名**：用 `提速 A→B`（= A 核时 ÷ B 核时，≥1 = 后者更快），
  不用 `B÷A` 这种能同时被读成"延迟比"和"加速比"的写法；
- 与参考实现比用 `参考÷本实现`（≥0.8 达标），并逐版本各给一列（看与参考的距离变化）；
- Δ 一律 `（新−基）`（负 = 变快），表下写口径注释；
- **表格由脚本从原始数据直出**（CSV / 日志解析），不要手抄数字——手抄必错。

### 负结果也是成果

"试过、量过、关闭"的内容与正收益同等重要：每条必须带**实测证据**
（交错 A/B 的差值区间、消融量级、或死锁/超时的事实）与处置结论。
